# 데이터베이스 설계

## 1. 설계 목표

회원 정보를 안전하게 관리하고, 외부 공공 API에서 가져온 혜택 정보를 필요에 따라 저장하거나 갱신할 수 있도록 설계합니다.

## 2. 테이블 후보

### users

| 컬럼 | 설명 |
|---|---|
| `id` | 사용자 기본 키 |
| `email` | 이메일 또는 로그인 식별자 |
| `password_hash` | 해시 처리된 비밀번호 |
| `created_at` | 가입 일시 |

이메일 또는 로그인 ID에는 중복 방지 제약조건을 적용합니다.

### benefits

| 컬럼 | 설명 |
|---|---|
| `id` | 내부 기본 키 |
| `external_id` | 외부 API의 서비스 식별자 |
| `title` | 서비스명 |
| `description` | 서비스 설명 |
| `category` | 서비스 카테고리 |
| `target_info` | 지원 대상 정보 |
| `region` | 관련 지역 |
| `application_period` | 신청 기간 |
| `official_url` | 공식 안내 링크 |
| `updated_at` | 데이터 갱신 일시 |

실제 컬럼은 외부 API에서 제공하는 정보와 검색 요구사항에 따라 조정합니다.

### favorites (확장 기능)

| 컬럼 | 설명 |
|---|---|
| `id` | 기본 키 |
| `user_id` | 사용자 ID |
| `benefit_id` | 혜택 ID |
| `created_at` | 저장 일시 |

즐겨찾기를 구현하는 경우 사용자와 혜택의 관계를 관리합니다.

## 3. 테이블 관계

- 한 사용자는 여러 혜택을 즐겨찾기에 저장할 수 있습니다.
- 하나의 혜택은 여러 사용자에게 저장될 수 있습니다.
- 즐겨찾기는 `users`와 `benefits`를 연결하는 관계입니다.

## 4. 데이터 관리 원칙

- 비밀번호는 평문으로 저장하지 않습니다.
- 외부 API의 고유 식별자를 활용해 중복 저장을 방지합니다.
- 원본 데이터와 내부 검색용 필드를 구분합니다.
- 신청 기간이나 지원 대상 정보가 제공되지 않을 수 있으므로 누락 데이터를 고려합니다.
- 외부 API의 이용 조건과 갱신 정책을 확인합니다.

## 5. 기본형 구현 범위

초기 버전에서는 회원 정보 관리와 혜택 목록·검색에 필요한 기능을 우선 구현합니다.

혜택 데이터는 매 요청마다 외부 API에서 가져올지, DB에 저장한 뒤 갱신할지 실제 API의 호출 한도와 데이터 규모를 확인하고 결정합니다.
